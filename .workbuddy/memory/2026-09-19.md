## copilot-server-agent 并发与多租户安全一轮整改

按 review 的 P0/P1 清单改完（review 结论：不同 session 已隔离，但同 session 多 request 未串行 + ownership 不可信）。

关键改动：
- **streaming lock**：SSE chat 改为在 `withSessionLock` 内 `sendAndWait()`（`send()` 只入队就返回，锁不到 agent loop）；事件监听器也移进锁内，避免并发请求互收 delta。新增 `sseFail` 收尾 + 客户端断开 `session.abort()` 当前 turn。
- **attach lock**：`getOrResumeSession` 加 `sessionAttachLocks`，解决并发首访双附着。
- **lifecycle lock**：disconnect / permanent delete 走同一 session lock；delete 用 `disconnectUnlocked` 避免重入死锁。
- **Session Registry**（新 `server/src/services/session-registry.ts`）：持久 JSON（原子写 + 串行 mutate），替代内存 owners Map；`assertOwnership` 统一归属校验，仅单租户下允许 legacy 认领。listSessions 按 owner 过滤。

## health 徽章 "disconnected" 语义修正

现象：刚打开页面徽章显示 `Copilot: disconnected`，但功能正常。
根因：`SessionService.getStatus()` 把「client 懒加载未创建」等同于 disconnected；`/api/health` 不碰 runtime（避免探针风暴），所以未发起会话前永远是 disconnected。
改法（用户选「两者都做」）：
- `getStatus()` 三态：`connected` / `idle` / `error`（idle = client 未创建，中性色，不是故障）；types.ts 与 client Health 类型同步。
- 新增 `SessionService.warmup()` + `COPILOT_WARMUP`（默认 true），server 启动后后台建连，不阻塞监听、失败只记日志。
- `HealthBadge` 三态渲染：connected 绿 / idle 灰（「未启动（首次会话时连接）」）/ error 黄 + 原因。
- `/api/debug` 配置块补充 registryPath / trustIdentityHeaders / bashPolicy。
验证：3s 内 healthy 变 connected 且日志「预热完成」；`COPILOT_RUNTIME_URL` 指向死端口时显示 error + ECONNREFUSED 原因。

## 数据库默认改为 SQLite，PostgreSQL 降为可选（用户要求）

`node:sqlite` 在 Node 22.13 / 23.4 起**免 `--experimental-sqlite`**（22.5 加入但需 flag）→ 可以零依赖当默认后端，无需安装任何原生包。实测 Node 22.22.2 可用（仅 ExperimentalWarning）。

**核心设计：方言层，而不是两套仓储。** 新增 `db/dialect.ts`，把 PG 与 SQLite 的差异全部收敛成钩子，`execution/sql-repository.ts` 与 `human-tasks/sql-repository.ts` 只写一份：
- 占位符：PG `$1` / SQLite `?1`（SQLite 支持编号占位符，这是能共用 SQL 的关键）
- JSON 列参数：统一传 **JSON 文本**（PG 的 jsonb 会隐式转换），读时按方言 parse
- 数组命中（eligible_roles/users）：PG 用 `jsonb_array_elements_text(...) = any($n::text[])`，SQLite 用 `json_each(...) where value in (select value from json_each($n))` —— 比原来的 `?|` / `@>` 更可移植
- 布尔 → SQLite 必须转 0/1（**绑定布尔会抛错**）；`undefined` 也必须转 null（同样抛错）
- 聚合：PG 要 `::int`，SQLite 不要；`count(*) filter (where ...)` 两边都支持

**踩坑（重要）**
- SQLite `pragma foreign_keys` **默认关闭**，不显式开 `on delete cascade` 完全无效（tests 里专门断言了这点）
- 事务内若再调外层 `query()` 会**自己等自己（死锁）** —— 执行器把所有语句串行化到一条 promise 链上，`transaction(fn)` 持有锁后，回调内必须用传进来的 `tx`
- 时间戳列**不要设 SQL default**：SQLite 的 `CURRENT_TIMESTAMP` 产出 `YYYY-MM-DD HH:MM:SS`，与 ISO 混排会破坏排序。全部由应用层显式写 ISO
- schema 写成 TS 常量（`sqlite-schema.ts`）而不是 `.sql` 文件：`tsc` 只产 JS，运行时去磁盘找 `src/**/*.sql` 在容器里会失效（已实测 dist 能独立跑通）
- SQLite 单写者 → `replicas` 必须为 1；库文件必须在持久卷上

**顺带修的真实缺陷**：`human_task.update` 的字段映射漏了 `eligibleRoles` / `eligibleUsers`，调用方改这两个字段原本**静默无效**（老 PG 实现同样有）。测试写出来才发现。

**测试**：40 项。`sqlite.test.ts` 在临时文件上跑，并用 close → 重新打开断言「重启后 data 仍在」（durable 的核心承诺）；`schema.test.ts` 升级为解析**两份 DDL** 逐列比对 + 校验代码引用的列两边都存在 —— 这是防「两个后端漂移」的关键护栏。

**向量检索**：没有语义检索需求（无 embedding 通道）→ **不建空壳**。留接入点：`COPILOT_SQLITE_EXTENSIONS` 可加载 sqlite-vec（执行器已支持 `loadExtension`，失败只记日志），PG 侧可上 pgvector + 在 dialect 加距离函数钩子。要真做需补 embedding 通道 + 一张 `agent_embedding` 表 + 一次 kNN 查询。

## Session 访问模型：single / shared 正式建模（用户长评驱动，159 条要求）

把隐含的「一 owner + 一个 Copilot session」显式建模成 `collaborationMode: 'single' | 'shared'`。
**命名刻意避开 `mode`**：SDK 的 `mode: "empty"` 是 runtime/工具模式，两者不能混。

**分层（新增 `server/src/collaboration/`）**：`CollaborationService`（按模式分派提交）/
`SessionCoordinator`（per-session 队列调度）/ `MessageService` / `ParticipantService` /
`SessionEventService` + 三个仓储（SQL 一份实现 + memory）。访问判定单独一个
`services/session-access.ts`：`resolve(sessionId, principal) → {mode, role, owner}` +
`assertCanView/Send/ManageMembers/Delete`。原来承担一切的 `assertOwnership` 收窄成
`assertOwner`（只回答"你是 owner 吗"）。

**几个关键设计决定**
- **`collaborationMode` 不属于 `PersistedSessionConfig`**：那是给 SDK 的 resume 配置；模式是业务会话
  元数据，落在 `agent_session.collaboration_mode`。`resume` 传模式直接 400；存储层 `update` 不写这一列，
  只有 `setCollaborationMode` 能改 → "模式不可变"在存储层也成立。
- **队列就是 `agent_execution` 表本身**：`status='created'` 即"排队中"，不另建队列表。
  `drain` 用 per-session 链式 promise 串行（不丢唤醒），取活按 `created_at, execution_id` 定序
  （毫秒时间戳会并列，加确定的次级键让两个后端给同一答案）。
- **`agent_execution` 拆成两个身份**（这是本次发现的真 bug，不只是命名问题）：
  `user_id` = **会话 owner**（数据归属；`resumeExecutionSession` 会拿它过 `assertOwner`，
  shared 里发起人只是 member，用发起人会被 registry 拒掉），`initiated_by_user_id` = **发起人**
  （审计 + SoD"发起人不能自批"，`human_task.initiated_by` 也改取它）。
  写文档/字段注释时把这条讲清楚，否则很容易被"优化"回单个字段。
- **`session_event` ≠ `execution_event`**：协作时间线（全体参与者可见、SSE 游标续传）vs 审计证据链。
  token 级 `assistant.delta` 只 SSE 不落库（写放大）。
- **消息 `sequence` 从 `agent_session.message_sequence` 原子自增**（`update ... returning`），
  不用时间戳：并发下会并列。`client_message_id` 做幂等键（重试不产生第二次 execution）。
- **execution / human task 可见性跟着 session 走**（`visibleSessionIds`）：shared 里参与者要能看到
  同会话中别人发起的执行与待办；按 tenant/user 过滤会正好漏掉它们。
- **`router.delete('/:id')` 用 `assertCanDelete`，成员退出走 `POST /:id/leave`**：
  业务退出 ≠ 技术脱离，一个 member 不该把别人的 Copilot session 摘掉。
- **单副本前提**：进程内队列 + 进程内事件广播 + 内存 session 锁 → `replicas: 1` 不变。
  多副本方向写进 architecture 第 7 节：advisory lock + DB 租约 + runtime affinity。

**排除项（明确不做）**：参与人私有上下文、按参与人切 MCP/runtime、运行中改模式、Redis/Kafka/Temporal。

## 老库补列：`create table if not exists` 不补列（真 bug，被测试逼出来）

`wiring` 相关测试 import 时连的是真实 `~/.copilot/agent.db`（早于本次 schema 改动建的），

## 错误 → 状态码：从「按文案猜」收敛成单一真相源

冒烟发现 **observer 发消息返回 500 而不是 403**：`sendServiceError` 用 `/无权访问/` 精确匹配，
而访问判定对"能不能写"抛的是「无权**发消息到** session」（`PERMISSION_LABEL.send='发消息到'`），
于是落 `next(err)` → 500。同类漏网还有「无权管理成员」「无权删除」「无权委派」「无权取消」「无权审批」。

顺着查下去发现更一般的毛病：**同一套分类正则抄了两份**（`routes/shared.ts` 的 `sendServiceError`
与 `middleware/errorHandler.ts`），必然漂移。而且分类是**白名单**，任何新文案都会静默掉到 500——
实测又抓到一批业务规则文案全在 500：`不能添加参与人`（single 模式）、`已经是该会话的 owner，无需添加`、
`不能移除会话 owner`、`owner 不能退出自己的会话`、`顺序审批未轮到该角色`、`session 已存在且归属不同`。

改法：
- 新增 `middleware/error-status.ts` 导出 `serviceErrorStatus(message)`，**路由与兜底共用一份**：
  无权前缀族 → 403；不存在/无法恢复/无法删除 → 404；调用方写错 → 400；认不出 → `undefined`（留给 500）。
- 400 族补齐：`不能 | 没有 | 无需 | 已经 | 未轮到`（业务规则）与 `已存在 | 已关闭 | 已过期`（状态冲突）。
- **判据刻意用具体词，不用「已」「未」单字**：`ActionService 未注入（wiring 缺失）`、
  `execution 写入通道尚未装配` 是服务端装配故障，必须留 500。放宽到单字会把"服务端炸了"伪装成"用户传错了"。
- 新增 `test/http-errors.test.ts`：**逐条覆盖真实抛错文案**的四档清单（403/404/400/未识别），
  且每条都同时验两条路径得出同一状态码；另有一组 internal 文案断言必须保持 500。
  **新增抛错文案必须补进那张表**，否则会静默退回 500/400。

**顺带删掉死代码**：`server/src/execution/store.ts`（仓储重构后零引用、`types.ts` 已有同名
`ExecutionRecord`，留着就是下一处漂移源）连同 dist 产物一起删除，typecheck/build/test 复核通过。

## 坑：冒烟跑的不是新代码 —— 旧进程占着端口

改完 403 后冒烟**仍然 500**，且文案证明是旧逻辑。根因：上一轮会话留下的 boot 进程
（`node dist/index.js`，已跑 5 分钟）仍占着 `:3999`，新进程 bind 失败退出，
而 health 探测**瞬间就通**（打到旧进程上），所以看起来"服务起来了"。
**判据是空日志**：正常启动必定打印 `[wiring] durable state = ...` + `[server] listening on ...`，
本次日志一片空白 —— 这是"你的进程没起来、在被别的进程服务"的信号。

排查/预防：
- 起服务前先 `lsof -nP -iTCP:<port> -sTCP:LISTEN` 看**监听者 PID 与年龄**（`ps -o etime`），
  重启前 `pkill -f "node dist/index.js"`。
- health 一通就继续是不够的，**要确认 boot 日志出现**。
