## Skill Flow / WorkflowRunner 三项加固（基于代码评审）

基线 commit `c43e74c`。评审结论：架构方向没问题，不需要推翻重做，改 failure semantics 与 step durability。

### 1. P0 runner 异常收尾（`server/src/workflow/runner.ts`）
- `runDetached()` 原来只 `console.error`，未预期异常会留下永远 `running` 的 execution。
- 改为：catch → `executions.get` → 非终态则 `executions.fail(id, err)`；连落 failed 都失败再 log。
- 需要 `import { isTerminal } from '../execution/types.js'`。
- 注意：`runSubagent`/`runGate` 自己 catch 了节点内失败（那是可路由出口），所以这条路径测试里不容易碰到，必须专门写用例（monkey-patch `executions.updateWorkflowState` 抛错来模拟）。

### 2. step durability：`WorkflowState.stepStatus`
- 新增 `WorkflowStepStatus = 'pending' | 'running' | 'waiting' | 'completed'`（optional，老数据按 pending）。
- `loop()` 里**先落 `running` 再执行节点**，执行完落 `{current: next, stepStatus: 'pending'}`；
  review/action 等人工落 `waiting`；`@stop`/`@end` 落 `completed`。
- 新增 `admitInterruptedStep()`：恢复时若 `stepStatus === 'running'` →
  `REPLAY_SAFE_NODE_TYPES = {agent, gate}` 允许重放（记 `workflow.step.interrupted` 审计）；
  `@action` **不重放**，落 failed 交人工核对（幂等键防不了"外部已生效但本地没记上"）。
- 新事件类型 `EVT.workflowStepInterrupted = 'workflow.step.interrupted'`。
- `workflow_state` 是 JSON blob 列，加字段不需要迁移。

### 3. validator 禁止同一出口多条 route
- 新增 `checkDuplicateOutcomes()`，code `route-outcome-duplicate`，节点与 `@flow` 的 `start` 都查。
- 原因：`findRoute()` 是 `routes.find(...)`，第二条静默失效。
- parser 已按 `on->to` 去重，所以"完全重复的同一条"不算歧义。

### 4. `@subagent` → `@agent`（旧名保留为别名）
- 语义澄清：它跑的是**当前 session 的又一次 agent turn**（`runExecutionTurn`），不是真正的 subagent 委派。
- parser 用 `BLOCK_ALIASES = { subagent: 'agent' }` 归一化，下游只认 `agent`。
- `FlowNodeType` 里 `'subagent'` 已移除；`runSubagent` 改名 `runAgent`。
- **不要动** `subagent.*` SDK 生命周期事件（`agent-runner.ts` / `agent-events.ts` / `Chat.tsx` / SSE `subagent` 帧）—— 那是另一回事。

## Skill Flow 第四轮加固（基线 `88a190d`）

评审的 10 条全做完，核心是**把"不确定的中间态"消掉**。19 改 + 1 新测试文件，
1340 insertions / 166 deletions。`tsc --noEmit`（src + test）✅ / `npm test` → **196/196** ✅（179 → 196）。

### 1. 🔑 等待态落库顺序反转（本轮最重要）
**旧顺序**：`create HumanTask` → `transition(execution = waiting_for_approval)` → CAS 写
`workflow.stepStatus = waiting`。中间崩 → `execution = waiting_for_approval` + `workflow = running`
+ 任务已建但 `waitingTaskId` 没落。这个态**不可判定**：没有任何字段能说明"到底该不该续跑"。

**新顺序**（`runActionStep()` 与 `pauseForReview()` 同步改）：
```
create HumanTask → CAS 写 workflow = waiting + waitingTaskId → transition(execution = waiting_for_approval) → 事件
```
崩在任何一步都**可判定**：`stepStatus === 'waiting'` 但 `waitingTaskId` 缺 → 直接 failed；
`stepStatus === 'waiting'` + 有 `waitingTaskId` → `run()` 开头的 `reconcileWaiting()` 补
`running → waiting_for_approval`（事件 `workflow.waiting.reconciled`）。

代价：可能留下**孤儿人工任务**（任务建了、状态没落）。接受这个代价换可判定性 —— 孤儿任务靠
过期 + 四重绑定检查自愈，不写专门的清理器。CAS 冲突时走 `orphanTaskNote()` 记
`workflow.orphan_task`（**不要**复用 `workflow.write.conflict`，语义不同）。

契约：`runtime.runAction()` **只建任务，绝不碰 execution 状态**（单写者原则）。
`ExecutionService.proposeAction()` 新增 `workflow.deferWaitingTransition?: boolean` ——
置位时只建任务 + 发 `approvalRequired`/`humanTaskCreated` 事件就 return，不 transition、
不发 `waitingForApproval`（那是调用方的事）。

连带：`@review` 加进**不可重放**集合（原 `REPLAY_SAFE_NODE_TYPES` 只有 agent/gate）。
理由：`@review` 的"已完成产物"是一个人工任务，若崩在 `waitingTaskId` 落库前，
这个产物在持久化状态里**不可见** → 重放会建第二个任务。`@review` 中断的提示文案改成指向
"我的任务"（类型感知），因为审批入口在前端。

### 2. `COPILOT_WORKFLOW_REQUIRE_AGENT_OUTPUT` 默认翻成 true
`@agent output:` 从"可选"变"默认必填"（`agent-output-missing`）。

### 3. 🔒 mcp/shell 从"配置默认"升格为"代码硬禁"

## 第四轮自查补丁（同一轮，199/199）

自己对第四轮 diff 做了一遍评审，找到一个**第四轮没闭合**的洞，外加一个**既有地雷**。

### A. `reconcileWaiting()` 只看 durable 字段 → 会永久卡死（第四轮引入）
`running` + `stepStatus = waiting` + `waitingTaskId = T` 这个形状有**两个来源**：
- 甲：崩在"落 waiting"与"迁移 execution"之间 → T 还 open，该等它；
- 乙：崩在 `resumeInto()` 的"`ensureRunning` 推出等待态"与"CAS 写 `current = next`"之间
  → T **已经被处理过**（那次续跑正是在处理它）。

第四轮的 `reconcileWaiting` 一律按甲处理 → 把 execution 推回 `waiting_for_approval`
等一个**永不再来的回调**；而 `ExecutionService.complete()` 在 `waiting_for_approval` 下是
**静默 return**，所以流程**永久卡住**，超时也救不回来（超时只对 open 任务产生回调）。

修法：`reconcileWaiting` 回查 `humanTasks.get(taskId)`，按任务**实时终态**分派：
- `open` → 甲，补迁移；
- 已收敛 → 摆回 `waiting_for_approval`（满足四重绑定）后 `resumeFromTask()` 原样重放；
- 查不到 → 落 failed，不瞎猜。

顺带覆盖了"**停机期间任务自然过期/被取消、回调没送达**"—— 之前也是永久卡死。

### B. `failWorkflow()` 在等待态会抛"非法状态迁移"（既有 bug）
`ALLOWED_TRANSITIONS` 里 `waiting_for_approval` / `waiting_for_input` 只有
`resuming / rejected / cancelled / expired`，**没有 `failed`**。
所以等待态调 `failWorkflow()` → `fail()` → `transition()` 抛异常；而它跑在**收尾路径**上，
异常往上抛的结果是 execution **反而永远停在等待态**（`runDetached` 兜底 catch 再调一次
`fail()` 还是同一个异常，只剩一行日志）。

受影响的不止新增代码：`resumeFromTask()` 里"节点不存在"、"input_submitted 不接受"、
`loadChecked()` 失败这三条**原本就会抛**。而"状态与任务对不上"这类内部不一致恰恰
最常发生在等待态 —— 最需要落 failed 的地方正好落不下去。

修法：新增 `exitWaitingIfNeeded()`，等待态先补一次 `→ resuming`，再走
`resuming → failed`（表里已有的边，语义也对："本来要恢复，恢复不了"）。

### 教训（已写进新 skill）
**"可判定" ≠ "判定正确"** —— 把不可判定换成判错只是换了个 bug。
指针字段记的是"被引用对象被创建过"，不是"它还没结束"；对账必须**解引用**。

### 验证

续跑中途崩→补完、停机期间过期→收敛、任务不存在→failed）。

## 第五轮：Skill Flow 四层分层（AST 正式化 + 控制流分析）

用户给了 `docs/sequence.md`（一份四层架构提案），本轮按它实现。

### 流水线（定稿）

```
SKILL.md → flow-parser.ts → FlowAst → flow-validator.ts → FlowDefinition → flow-analyzer.ts → issues
                                                                                  ↓
                                                                            WorkflowRunner
```

| 层 | 文件 | 输入 → 输出 | 回答 |
|---|---|---|---|
| 语法 | `skills/flow-ast.ts`（新） | — | 类型定义 |
| 语法 | `skills/flow-parser.ts` | Markdown → `FlowAst` | 作者**写了**什么 |
| 语义 | `skills/flow-validator.ts` | `FlowAst` → `FlowDefinition` | 允许执行什么 |
| 控制流 | `skills/flow-analyzer.ts`（新） | `FlowDefinition` → issues | 图的形状对不对 |
| 编排 | `workflow/runner.ts` | `FlowDefinition` → 推进 | 怎么跑 |

### 关键决策（与用户提案的三处偏离，都写进了注释）

1. **属性用有序数组，不用 `{role?: string; strategy?: 'ANY'|'ALL'}`**：
   ① 报错要指到属性自己那一行 → 行号必须随属性走；
   ② `'ANY'|'ALL'` **表达不了** `strategy: all` 这种"写了但不合法" —— 而用户自己
   说"AST 可以带 invalid role"。类型化 = 把合法性判定偷偷搬进语法层。
2. **`@flow` 用 `flows: FlowAstFlow[]` 而不是单个 `flow`**：作者可能写 0 个或 2 个，
   `flow-missing` / `flow-duplicate` 两条检查得报得出来。定成"必然恰好一个"等于让
   语法层替语义层做决定。
3. **route 带 `line`**（`FlowAstRoute {outcome, target, line}`）：重复出口的报错从
   "节点标题行"改成"重复的那一条自己的行"。AST 用作者视角的 `outcome/target`，
   `FlowDefinition` 用紧凑的 `on/to`，中间那次映射是两层的接缝。

### 新增：`FlowIssue.severity`

`severity?: 'error' | 'warning'`，**缺省 error**（新增检查默认拦住；反过来会让新检查静默失效）。
`hasBlockingIssue()` 统一判定。`FlowValidationResult.definition` 现在只在无 error 时给出。

### 新增：`flow-analyzer.ts` 三条检查（刻意互不重叠）

- `node-unreachable`（error）：从 start 走不到 → 永远不会被执行。
- `no-terminal-path`（error）：**可达**节点出发到不了任何终态 → 走进来就出不去。
  只查可达节点（不可达的已报过，叠一条是噪音）。
- `no-success-path`（warning）：**整条流程没有任何 `@end`** → 只可能以失败收尾。
  ⚠️ 第一版写成"start 到不了 @end"，与 `node-unreachable` **完全重叠**
  （`@end` 到不了 ⇔ 它不可达）→ 同一个问题说两遍。改成"有没有 @end 节点"后不重叠。
- **环本身不报错**（打回重做是常态）；要拦的是**没有出口的环**，恰好被 `no-terminal-path`
  覆盖 —— 用"活跃性"表达比"找环"更准，也少一个概念。
- 图就是 `Map<string, Set<string>>` 局部变量，**不建 `cfg.ts`**（用户明确反对 over-design）。
- 结构错误存在时**不跑分析器**：边指向不存在的节点时分析器会得出"这个节点出不去"
  这种**错误**结论。与编译器"先报语法再报类型"同一节奏。

### 新增：`flow:lint` CLI

`server/src/skills/flow-lint.ts` + `npm --prefix server run flow:lint -- <路径...>`。
- 用**与生产同一份**注册表（`flowRegistryLookup` / `businessRoleLookup`）与配置
  （`config.workflowAgentTools` / `workflowRequireAgentOutput`）—— lint 与运行时判定不一致，
  它给的"通过"就是假的。
- 输出 `path:line ERROR|WARN code  message`，按行号排序，有 error 时退出码 1。
- 没有 flow block 的普通技能**跳过**（不算错误）。
- 参数可以是 SKILL.md / 技能目录 / 技能根目录。

### 连带修的两处

- `workflow.test.ts` 的 `SPIN_MD`（自环 gate）原本没有任何终态出口 → 现在被
  `no-terminal-path` 静态拦下，测不到步数上限兜底。加一条 `stop -> done` + `@end done`，
  并把 `stop` 加进该 gate 的 `outcomes` 声明。
  **两条闸门分工**：静态分析器只能证明"图上没有出口"，证明不了"审核人永远不同意"。
- `flow-validator.test.ts` 的 `ok()` 改成跑完整流水线（校验 + 分析），新增 `semantics()`
  只跑语义层 —— 用于验证"校验器不做图分析"这条分层边界。
