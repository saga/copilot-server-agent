# 金融 AI Agent 平台架构评审 Checklist

> 适用对象：金融服务领域内 AI Agent 平台的架构评审（立项评审、上线前评审、年度复审、并购尽调）。
> 使用方式：逐项回答「是 / 否 / 部分 / 不适用」，对「否」与「部分」给出证据、严重度、整改建议与期限。
> 设计目标：不追求面面俱到，而是最大化覆盖**会导致资金损失、越权、合规事故、审计失败的严重问题**。

---

## 0. 评审的最高层不变量（Invariant）

评审任何一条之前，先确认平台是否守住这四条底线。任何一条被突破，直接判 P0。

1. **Runtime 可以拥有 autonomy，但不能拥有 enterprise authority。** Agent 可以自主推理、规划、选工具，但授权、状态、合规控制的最终权威在确定性系统。
2. **Control Plane 决定是否允许，但不替代 Domain 成为 Business Truth。** 业务事实（订单状态、持仓、客户状态）的权威来源永远是领域系统。
3. **Workflow 拥有 execution state（当前节点、待审批、重试次数），但不拥有 business state。**
4. **Agent Memory 可以缓存、引用、摘要业务状态，但不能作为业务事实的权威来源（Source of Truth）。**

## 严重度定义

| 级别 | 含义 | 处置要求 |
| ---- | ---- | -------- |
| **P0** | 红线。可能导致资金损失、越权执行、监管处罚、审计失败 | 上线前必须修复，无豁免 |
| **P1** | 重要。显著放大风险或在故障时失去保护 | 本期必须修复或给出带期限的整改计划 |
| **P2** | 健壮性。降低工程质量与可运维性 | 纳入 backlog，下一迭代处理 |

## P0 红线速查表（先查这 10 条，任何一条不通过即中止评审）

| # | 红线 | 对应条目 |
| - | ---- | -------- |
| 1 | 存在 LLM 输出**直接**触发业务副作用（写库/下单/转账）的通路 | A3 / F1 |
| 2 | Agent Memory 被当作业务事实的权威来源 | B3 / H2 |
| 3 | 工具调用**不经过**外部授权检查，靠 Agent 自行判断 | D1 |
| 4 | 高危操作没有风险分级监督，全部自动执行（或相反：全部裸人工） | G1 |
| 5 | 审批不绑定具体 Proposal（参数/金额/版本），存在 replay 或 scope creep | G2 |
| 6 | RAG / 检索不做租户与数据权限过滤，"查到即塞入 prompt" | E1 |
| 7 | 副作用无幂等键，重试可产生重复扣款/重复下单 | F2 |
| 8 | 审计日志缺失或可篡改，无法重建"谁在何时因何批准了什么" | K1 |
| 9 | Workflow 崩溃恢复后会重复执行已完成的副作用 | C4 / L3 |
| 10 | Prompt injection 可突破授权边界（注入文本能触发未授权工具调用） | J1 |

## A. 总体架构与权威分离（8 项）

### A1. 是否明确划分了「LLM 可决定」与「必须确定性系统决定」的边界？
- **严重度**：P0
- **检查要点**：要求平台方用一页纸列出：哪些决策允许 Agent 自主（推理、拆解、工具选择），哪些必须外部约束（授权、状态迁移、合规）。注意措辞：合理的表述是"LLM 在关键控制路径上不应是唯一、不可约束的权威"，而不是泛泛的"LLM 不能做 X"——后者通常意味着没人认真想过边界在哪。
- **建议 / 参考方向**：画出 Authority Separation 图（Runtime Reasoning / Control Plane Policy / Domain Truth 三层）。参考 AWS Agentic AI Lens 对 orchestration layer 控制点的要求。

### A2. Agent Runtime 是否被错误地当作信任边界？
- **严重度**：P0
- **检查要点**：检查安全模型文档。如果"请求来自 Agent Runtime 内部"被当作放行理由，即不通过。Runtime 是执行环境，不是信任边界；每个出站调用都必须独立鉴权。
- **建议 / 参考方向**：零信任原则——tool gateway 对每个调用独立做身份认证 + 授权，不假设调用方可信。

### A3. 是否存在 LLM 输出直达业务副作用的通路？
- **严重度**：P0
- **检查要点**：任选一个写操作（如下单），从 LLM 文本输出出发逐跳追踪到 DB/交易系统，确认中间存在：schema 校验 → 策略判断 → 授权 → Domain 不变量校验。任何一跳可绕过即不通过。
- **建议 / 参考方向**：所有副作用收敛到统一 Command 通道（见 F1），LLM 只能产出「意图/提案」，永远不能产出「已执行的副作用」。

### A4. Control Plane 与 Agent Runtime 的职责是否文档化分离？
- **严重度**：P1
- **检查要点**：Control Plane 应至少包含：Agent/Skill/Tool Registry、Policy、Authorization、Workflow、Human Task、Command、Audit。检查是否每个组件都有明确归属（属于 Control Plane 还是 Runtime），是否存在"两边都管"或"没人管"的灰色地带。
- **建议 / 参考方向**：Workflow 是 Control Plane 中负责 Business Execution / State Transition 的核心组件（Workflow ∈ Control Plane，而非 Workflow = Control Plane）。注意这是主流厂商正在趋近的**架构模式**，各家的术语并不统一——评审时看职责划分是否清晰，不纠结命名。

### A5. 「关键控制路径」与「非关键路径」是否区别对待？
- **严重度**：P1
- **检查要点**：低风险只读场景（摘要、翻译、检索问答）如果也被要求走全套审批，说明设计没有风险分层，会导致团队绕过体系"抄近路"。反之亦然。
- **建议 / 参考方向**：按风险 × 可逆性 × 金额 × 影响面划分路径等级，控制强度与风险成正比（proportionate control）。

### A6. 是否存在绕过 Control Plane 的"快捷通道"？
- **严重度**：P0
- **检查要点**：grep / 审查代码库中直接写库、直接调交易 API 的 Agent 工具；检查是否有"临时脚本""管理员后门"未走 Command 通道。
- **建议 / 参考方向**：网络层强制——Agent Runtime 所在网段无法直连业务 DB，所有出站必经 gateway。

### A7. 对任意一笔副作用，能否指出授权发生在哪一跳？
- **严重度**：P0
- **检查要点**：随机抽 3 个写操作，要求现场指出 Policy Enforcement Point（PEP）的确切位置与代码入口。答不出或答案是"Agent 自己会判断"即不通过。
- **建议 / 参考方向**：PEP 必须在 Agent 之外的确定性组件（tool gateway / command service）。

### A8. Agent 自主程度是否随风险等级动态调整？
- **严重度**：P1
- **检查要点**：检查是否存在 autonomy 分级配置（如只读建议 → 需确认 → 可自动执行），还是所有场景一刀切。
- **建议 / 参考方向**：Autonomy Level 与 Oversight Policy 联动：风险越高，自主半径越小。

## B. Agent 本体设计（7 项）

### B1. Agent 的系统提示词是否承载了权限语义？
- **严重度**：P0
- **检查要点**：检查 system prompt 中是否出现"你可以执行 X""你被禁止 Y"并以此为唯一防线。Prompt 是建议，不是控制；注入即可改写。
- **建议 / 参考方向**：权限只由 Control Plane 的策略引擎表达；prompt 里的行为规范只是体验层。

### B2. Agent 的规划深度、步数、成本是否有硬上限？
- **严重度**：P1
- **检查要点**：检查 runner 是否有 max steps / max tokens / max wall-clock / max cost 四类熔断，超限后的行为（fail-safe 还是继续跑）。
- **建议 / 参考方向**：默认 fail-closed；超限事件入审计并告警。

### B3. Agent Memory 是否被当作业务事实使用？
- **严重度**：P0
- **检查要点**：检查 Agent 是否会基于 memory 中的"该订单已审批"直接推进后续写操作，而不回查 Domain 系统。这是最常见也最危险的设计错误之一。
- **建议 / 参考方向**：memory 中的业务数据一律标记为缓存/摘要，关键决策前必须从权威源重读（read-through）。

### B4. Agent 动态选择工具 / 子 Agent 是否受白名单约束？
- **严重度**：P0
- **检查要点**：Agent 能否调用注册表之外、或当前用户/租户未被授权的工具？动态 orchestration（Agent 自行委派）本身合理，但候选集必须是 approved scope。
- **建议 / 参考方向**：工具选择 = 从策略过滤后的 capability set 中选；集合本身由 Control Plane 决定，不由 Agent 决定。

### B5. Agent 输出是否有强 schema 校验？
- **严重度**：P1
- **检查要点**：检查结构化输出（JSON）是否经过 schema 校验 + 字段级合法性检查（金额为正、账户存在、枚举合法），校验失败的行为是什么。
- **建议 / 参考方向**：校验失败的输出不得进入下游任何状态迁移；记录失败样本用于评测。

### B6. 多 Agent 委派链是否可追溯、可限制深度？
- **严重度**：P1
- **检查要点**：orchestrator → sub-agent → sub-sub-agent 的链长是否有限制？一次用户请求产生的完整调用树能否事后还原？
- **建议 / 参考方向**：委派深度上限 + 每跳在审计事件中记录 parent_execution_id。

### B7. Agent 能否自行扩大自己的能力边界？
- **严重度**：P0
- **检查要点**：Agent 是否能在运行时装载新工具、修改自己的 prompt、注册新 skill、申请新凭证？任何"自我扩张"能力都是红线。
- **建议 / 参考方向**：能力变更走与代码变更同级的变更管理流程（评审 + 灰度 + 回滚）。

## C. Workflow 与编排（9 项）

### C1. Workflow 定义是否确定性、版本化、可评审？
- **严重度**：P0
- **检查要点**：流程定义是代码/声明式文件（入版本库、走 code review），还是由 LLM 在运行时即时生成？后者在关键路径上不可接受。
- **建议 / 参考方向**：确定性流程定义 + 版本号；LLM 可在受控范围内选择走哪条已定义的路径，不发明新路径。

### C2. 状态机是否拒绝非法迁移？
- **严重度**：P0
- **检查要点**：构造非法迁移测试（如 draft → executed 跳过审批），确认被运行时拒绝而非静默接受。
- **建议 / 参考方向**：显式状态机，迁移表即策略；非法迁移记录审计事件并告警。

### C3. Workflow execution state 与 business state 是否分开存储？
- **严重度**：P1
- **检查要点**：`workflow.currentNode / pendingApproval / retryCount`（执行状态）与 `order.status / position.quantity`（业务状态）是否分属不同存储与不同权威。混在一处会导致两边都说不清谁是 SoT。
- **建议 / 参考方向**：三分法——Agent Memory = contextual state（权威：Agent Runtime）；Workflow = execution state（权威：Control Plane）；Business = domain state（权威：Domain 系统）。

### C4. 崩溃恢复语义是否安全（不重复执行、不丢人工节点）？
- **严重度**：P0
- **检查要点**：在副作用执行前后各注入一次进程崩溃，重启后验证：已完成的副作用不重复、等待人工的任务可恢复、状态机不错位。特别注意"先执行后落库"的窗口期。
- **建议 / 参考方向**：先写执行状态再执行节点（write-ahead）；副作用带幂等键使重复执行无害；恢复流程有专门的故障演练。

### C5. 人工节点是否是一等公民（暂停-恢复语义）？
- **严重度**：P1
- **检查要点**：HITL 是流程内的显式节点（状态 = waiting，可恢复、可超时、可审计），还是流程外的"发邮件等人回复再手动点按钮"？
- **建议 / 参考方向**：Human Task 作为 workflow 的原生节点类型；恢复事件驱动状态机推进。

### C6. 流程定义变更如何影响在途实例？
- **严重度**：P1
- **检查要点**：SKILL/流程文件改了之后，已在运行中的实例按新定义还是旧定义走？若无版本钉住，同一实例前后语义不一致，审计无法重建。
- **建议 / 参考方向**：实例启动时记录定义版本/hash，全程按该版本执行；定义变更只影响新实例。

### C7. 是否有步数/时间/成本的流程级兜底？
- **严重度**：P1
- **检查要点**：死循环路由、互相踢皮球的子流程，靠什么停下来？
- **建议 / 参考方向**：流程级 max steps + 超时；超限进入人工处理队列而非静默失败。

### C8. 若允许 Agent 动态编排（agent-delegated orchestration），外层是否有确定性护栏？
- **严重度**：P0（如允许动态编排）/ 不适用（如不允许）
- **检查要点**：AWS Agentic AI Lens 同时承认 deterministic workflow 与 agent-delegated workflow 两种模式，但要求**无论哪种**，authorization、state protection、input validation、circuit breaker 都在 orchestration layer 上。检查护栏是否齐全。
- **建议 / 参考方向**：动态编排只决定"调用哪个已批准的组件"，授权与状态保护不随之动态化。

### C9. 流程每一步是否产生审计事件？
- **严重度**：P1
- **检查要点**：step started/completed/waiting/resumed/failed 是否全部入审计流，且带 correlation id 串联。
- **建议 / 参考方向**：事件流即审计底稿；事后可由事件重放整个流程。

## D. 授权与能力边界（10 项）

### D1. 每次工具调用是否都经过外部授权检查？
- **严重度**：P0
- **检查要点**：是**每一次**，不是首次或会话级一次。检查 gateway 代码路径，确认没有缓存授权结果跨调用复用（除非有显式 TTL 与撤销机制），确认不依赖 Agent 自报"我有权限"。
- **建议 / 参考方向**：per-invocation authorization at the tool gateway，与 AWS Agentic AI Lens 的 tool usage 安全要求对齐。

### D2. Agent 的有效能力（effective capability）是否被外部约束？
- **严重度**：P0
- **检查要点**：注意正确的表述不是"Tool 权限必须比 Agent 权限窄"（集合包含关系难以定义），而是：Agent 的有效能力 = 用户权限 ∩ 会话 scope ∩ 工具白名单 ∩ 策略决策，每一层都在 Agent 之外强制执行。
- **建议 / 参考方向**：能力收窄链：approved capability set → tool invocation → policy decision → domain authorization → side effect，逐层只可收窄不可放宽。

### D3. 权限模型是否租户级隔离？
- **严重度**：P0
- **检查要点**：跨租户测试：租户 A 的 Agent 能否通过构造参数访问租户 B 的数据/操作？检查所有查询路径（API、工具、RAG、缓存）的租户过滤是否一致。
- **建议 / 参考方向**：tenant context 由请求入口注入、全链路强制传递，不允许 Agent 指定或修改。

### D4. 每个工具的 scope 是否显式声明并最小化？
- **严重度**：P1
- **检查要点**：工具注册表中每个工具是否有声明：读/写、资源范围、金额上限、所需角色。存在"全能工具"（如任意 SQL 执行）即不通过。
- **建议 / 参考方向**：危险原语（raw SQL、shell、http 任意请求）不出现在 Agent 可达的工具集中。

### D5. 高危操作是否需要逐级增强的认证与确认？
- **严重度**：P0
- **检查要点**：大额转账、批量操作、权限变更是否有 step-up auth（二次认证/双人复核）？金额分级阈值在哪里定义、谁能改？
- **建议 / 参考方向**：阈值属于策略配置，变更走审计；分级模型见 G1。

### D6. 凭证是否按任务最小化下发？
- **严重度**：P0
- **检查要点**：Agent 拿到的 token 是宽权限长时效，还是按单次任务、单个工具、最小 scope、短时效签发？检查凭证是否出现在 prompt/日志中。
- **建议 / 参考方向**：just-in-time 凭证签发；凭证永不进入 LLM 上下文。

### D7. 授权决策是否可重放、可解释？
- **严重度**：P1
- **检查要点**：同样的输入重放策略引擎，是否得到同样的决策？每次决策是否记录命中的策略规则？
- **建议 / 参考方向**：策略决策日志包含：输入快照、命中规则、决策结果、策略版本。

### D8. 是否存在 wildcard 授权？
- **严重度**：P1
- **检查要点**：`*` 资源、`admin` 角色、永久授权、不限额授权。存在即逐个过堂：为什么需要、补偿控制是什么。
- **建议 / 参考方向**：persistent trust 限定到特定 command + 参数形状 + 资源范围（reference: AWS 对 persistent trust 的限制建议）。

### D9. 拒绝路径是否被测试（deny-by-default）？
- **严重度**：P1
- **检查要点**：测试用例中授权拒绝的覆盖是否充分？策略引擎故障时是 fail-open 还是 fail-closed？（后者才正确）
- **建议 / 参考方向**：策略引擎异常 = 拒绝 + 告警，绝不允许"策略服务挂了先放行"。

### D10. 是否存在 confused deputy 风险？
- **严重度**：P0
- **检查要点**：低权限用户能否通过诱导高权限 Agent/服务代为执行其无权执行的操作？重点检查：Agent 以服务身份运行时，原始用户的权限是否穿透传递。
- **建议 / 参考方向**：on-behalf-of 语义——下游授权始终以原始用户身份评估，Agent 自身身份只用于审计。

## E. 数据与 Data Entitlement（7 项）

### E1. RAG / 检索是否做租户级与行级权限过滤？
- **严重度**：P0
- **检查要点**："查到即塞入 prompt"是最常见的数据越权来源。检查检索层是否在向量召回后、拼接 prompt 前做 entitlement 过滤；用跨租户用例实测。
- **建议 / 参考方向**：entitlement 过滤在检索服务内强制（不由 prompt 嘱咐），过滤结果入审计。

### E2. 进入 prompt 的数据是否有最小化原则？
- **严重度**：P1
- **检查要点**：是否把整表/整文档塞入上下文？数据最小化既是安全问题也是成本问题。
- **建议 / 参考方向**：字段级裁剪 + 按需检索；敏感字段默认排除。

### E3. 敏感字段（PII、账户、证件号）进入 LLM 前是否脱敏？
- **严重度**：P0（涉及监管数据出境时）/ P1
- **检查要点**：检查脱敏管线位置（数据离开企业边界前必须完成）；如果模型为第三方 API，未脱敏直接发送通常违反监管要求。
- **建议 / 参考方向**：确定性脱敏（非 LLM 脱敏）+ 可逆映射留在企业域内。

### E4. 数据出境 / 出域规则是否明确？
- **严重度**：P0
- **检查要点**：哪些数据可以发送给外部模型 API？金融数据跨境是否满足当地监管（如境内金融数据不出境）？
- **建议 / 参考方向**：数据分类分级 + 路由策略联动（敏感数据只走本地/专有云模型，见 I1）。

### E5. Agent 日志与 trace 是否泄露敏感数据？
- **严重度**：P1
- **检查要点**：prompt 全文、工具返回、错误堆栈是否原样入日志？日志访问权限是否与业务数据同级管控？
- **建议 / 参考方向**：日志侧二次脱敏；审计日志与普通应用日志分流存储。

### E6. 推理数据与训练/微调数据是否隔离？
- **严重度**：P1
- **检查要点**：客户会话是否会被供应商用于训练（API 条款层面）？内部微调数据采集是否有同意与过滤机制？
- **建议 / 参考方向**：合同层面禁用训练使用；技术层面默认不回流。

### E7. 缓存（语义缓存 / memory）是否带 entitlement 维度？
- **严重度**：P1
- **检查要点**：用户 A 触发的缓存会不会命中用户 B 的相似问题并返回越权内容？
- **建议 / 参考方向**：缓存键包含租户/权限维度，或缓存仅用于公共知识。

## F. Command 与副作用执行（7 项）

### F1. 所有副作用是否收敛到统一 Command 通道？
- **严重度**：P0
- **检查要点**：数一下代码库里有几条写路径。理想答案：一条。每条额外写路径都是一处绕开策略/授权/审计的洞。
- **建议 / 参考方向**：Intent → Policy → Authorization → Command → Domain invariant → Side effect，全链路单通道。

### F2. 副作用是否有幂等键？
- **严重度**：P0
- **检查要点**：同一请求重放（网络重试、用户双击、崩溃恢复、队列重投）是否产生重复副作用？抽查代码确认幂等键贯穿到下游系统。
- **建议 / 参考方向**：客户端生成幂等键 + 服务端去重表；下游不支持幂等的，用补偿而非重试。

### F3. 超时与重试策略是否考虑副作用安全？
- **严重度**：P1
- **检查要点**：超时后重试一个"可能已成功"的写操作，是重复执行的标准事故剧本。检查重试策略是否区分读/写、是否依赖幂等键。
- **建议 / 参考方向**：写操作默认不自动重试，除非幂等保障完备；超时进入人工核查队列。

### F4. 多步副作用是否有补偿（saga）设计？
- **严重度**：P1
- **检查要点**：跨系统的多步写（如下单 + 扣款 + 记账）中途失败怎么办？逐个检查每个多步流程的补偿路径是否存在、是否被测试。
- **建议 / 参考方向**：每个可逆步骤定义补偿动作；不可逆步骤放在最后并有最强前置校验。

### F5. Domain 不变量是否在 Domain 层强制？
- **严重度**：P0
- **检查要点**："持仓不能为负""账户余额不能透支"等约束，是 DB/领域服务强校验，还是靠上游各层"自觉"？上游任何一层失守都应被 Domain 层兜住。
- **建议 / 参考方向**：不变量下沉到离数据最近的一层；上游校验只是体验优化。

### F6. 是否有资源版本/乐观锁防止"审批时看到的状态 ≠ 执行时的状态"？
- **严重度**：P0
- **检查要点**：审批人看到的是余额 100 万时批准的，执行时余额只剩 50 万——系统是否检测到版本变化并拒绝或要求重审？
- **建议 / 参考方向**：proposal 携带 resource_version，执行前比对，不一致则拒绝。

### F7. 副作用失败是否有告警与人工兜底？
- **严重度**：P1
- **检查要点**：写失败的命令去了哪？静默吞掉、无限重试、还是进入有人盯的队列？
- **建议 / 参考方向**：死信队列 + 值班告警 + 人工处置 SOP。

## G. HITL 与审批（8 项）

### G1. 监督策略是否按风险分级，而非"高风险一律人工审批"或"全部自动"？
- **严重度**：P0
- **检查要点**：正确模型是 risk-tiered oversight：风险 × 影响 × 可逆性 × 自主成熟度 → None / Monitor / Confirm / Approve / Dual Control。两个极端都不通过：全部自动（失控），全部人工（橡皮图章 + 团队绕行）。例如低金额自动退款应允许 policy + limit + 自动执行 + 事后抽查。
- **建议 / 参考方向**：五档监督矩阵，按业务线落地阈值；参考 AWS "proportionate human oversight"。

### G2. 审批是否绑定具体 Proposal？
- **严重度**：P0
- **检查要点**：审批对象必须包含：操作类型、参数、金额、资源、资源版本、有效期。批准"一个模糊意图"或"未来类似操作"（无 scope 限制的）即不通过——这是 approval replay 与 scope creep 的来源。
- **建议 / 参考方向**：审批即对具体版本业务状态的签名；pre-approved action class（见 G6）是合法例外，但必须有显式 scope。

### G3. 审批人是否看到足够的决策上下文？
- **严重度**：P1
- **检查要点**：审批界面是否展示：金额、对手方、变更前后 diff、Agent 的推荐理由、风险提示、数据来源？只显示"Agent 请求执行操作 X，同意/拒绝"的界面等于没有审批。
- **建议 / 参考方向**：审批 UI 是风控组件，按风控组件标准设计。

### G4. 职责是否分离（发起人不能审批自己的请求）？
- **严重度**：P0
- **检查要点**：检查审批人选择逻辑：发起人、同组、下级能否成为审批人？双人复核是否真的两个独立人？
- **建议 / 参考方向**：segregation of duties 规则在 Control Plane 强制，不靠流程约定。

### G5. 审批超时与拒绝后的流程走向是否定义？
- **严重度**：P1
- **检查要点**：超时是自动拒绝、升级、还是自动通过（危险）？拒绝后流程终止、回退、还是允许修改后重提？
- **建议 / 参考方向**：默认超时拒绝；所有走向在流程定义中显式建模。

### G6. 预授权 / standing approval 是否有显式 scope？
- **严重度**：P1
- **检查要点**：合法的预授权设计（如"基金经理允许 Agent 自动执行 < $100K 且符合策略 X 且风险等级 ≤ 2 且限定 Fund A 的操作"）必须四要素齐全：scope、限额、有效期、可撤销。检查是否存在没有这四要素的"无限授权"。
- **建议 / 参考方向**：预授权本身是带完整审计的一等授权对象，不是审批的缺失。

### G7. 是否有防"橡皮图章"机制？
- **严重度**：P2
- **检查要点**：统计审批时长分布——如果平均审批时间 < 3 秒，说明审批流于形式。是否有审批质量抽检、批量审批限制、强制阅读时间？
- **建议 / 参考方向**：审批行为分析 + 事后抽查 + 审批人问责。

### G8. 审批记录是否不可篡改？
- **严重度**：P0
- **检查要点**：审批记录（谁、何时、批准了什么版本、看到什么上下文）是否 append-only？能否事后修改或删除？
- **建议 / 参考方向**：审计流 WORM 存储；审批记录与执行记录交叉可验证。

## H. 状态管理三分法（5 项）

### H1. 三类状态是否有明确各自的所有者？
- **严重度**：P1
- **检查要点**：Agent context/memory（权威：Agent Runtime）、workflow execution state（权威：Control Plane）、business state（权威：Domain 系统）——架构文档中是否能指出每一类状态的存储位置与写入方。
- **建议 / 参考方向**：任何"同一个 status 字段三处都写"的设计都是事故温床。

### H2. Business state 的 Source of Truth 是否在 Domain 系统？
- **严重度**：P0
- **检查要点**：订单状态、持仓、客户风险等级等，是否存在 Domain 系统之外的"权威副本"？（缓存、投影、读模型都可以存在，只要明确它们不是权威。）
- **建议 / 参考方向**：关键决策前 read-through 到权威源；缓存只用于展示与非关键路径。

### H3. Agent Memory 中的业务数据是否明确标记为缓存/摘要？
- **严重度**：P1
- **检查要点**：memory 条目的 schema 是否区分"用户偏好/对话上下文"与"业务状态摘要"？后者是否带时间戳与来源？
- **建议 / 参考方向**：业务状态摘要条目带 as-of 时间戳，过期视为无效。

### H4. Workflow execution state 崩溃后可恢复？
- **严重度**：P0
- **检查要点**：执行状态（当前节点、重试计数、待办人工任务）是否持久化？内存态即不通过。与 C4 联动检查。
- **建议 / 参考方向**：durable execution state + 事件溯源。

### H5. 状态不一致是否有对账机制？
- **严重度**：P1
- **检查要点**：Workflow 认为"已执行"、Domain 认为"未执行"的错位，靠什么发现、靠什么修复？
- **建议 / 参考方向**：定时对账 job + 不一致告警 + 人工修复工具。

## I. 模型路由与供应商（5 项）

### I1. 模型选择是否由 Control Plane 策略决定？
- **严重度**：P1
- **检查要点**：模型路由（哪个任务走哪个模型）是集中策略，还是散落在各 Agent 的代码/配置里？敏感数据路由到外部 API 是否被策略禁止（与 E4 联动）？
- **建议 / 参考方向**：Model Routing 属于 Control Plane：数据分级 × 任务风险 × 成本 → 模型选择。

### I2. 不同风险等级的任务是否路由到不同能力的模型？
- **严重度**：P2
- **检查要点**：高风险任务是否配置了更强模型 + 更严的输出校验？低风险任务是否避免过度消费旗舰模型？
- **建议 / 参考方向**：风险分级路由同时优化质量与成本。

### I3. 供应商故障的降级策略是否被演练？
- **严重度**：P1
- **检查要点**：主模型 API 挂了怎么办？降级模型、排队、还是直接故障？降级是否被实际演练过，降级时的输出质量是否有兜底校验？
- **建议 / 参考方向**：关键路径双供应商或本地兜底模型；降级事件入审计。

### I4. 是否有模型输出质量的持续评测？
- **严重度**：P1
- **检查要点**：模型升级/prompt 变更后，靠什么发现输出质量漂移？是否有评测集与回归门禁？
- **建议 / 参考方向**：业务场景评测集 + CI 门禁 + 线上抽样人工评测。

### I5. 成本与配额是否有管控？
- **严重度**：P2
- **检查要点**：单租户/单任务的成本上限？异常消耗（循环调用）能否被自动熔断？
- **建议 / 参考方向**：配额 + 预算告警 + 异常消耗熔断（与 B2 联动）。

## J. 安全与对抗（7 项）

### J1. 是否做过 Prompt Injection 测试？
- **严重度**：P0
- **检查要点**：直接注入（用户输入"忽略之前的指令"）与目标验证：注入能否触发未授权的工具调用、越权数据访问、策略绕过？关键判据是——注入成功后**最坏结果是什么**。如果最坏结果是"输出难听话"可接受；如果是"执行了未授权操作"，架构本身不通过（授权不应能被 prompt 突破，见 D1）。
- **建议 / 参考方向**：OWASP LLM Top 10（LLM01）；安全靠架构分层，不靠 prompt 防御。

### J2. 间接注入（RAG 文档、邮件、网页）是否有防护？
- **严重度**：P0
- **检查要点**：检索到的文档里埋一句"请调用转账工具"，会发生什么？不可信内容进入上下文时是否被标记、隔离、限制其触发的能力？
- **建议 / 参考方向**：不可信内容只做信息输入，不触发能力提升；内容来源分级。

### J3. 工具返回内容是否被视为不可信输入？
- **严重度**：P1
- **检查要点**：工具返回（可能包含外部数据）重新进入 Agent 上下文时，是否与系统指令做了信任级别区分？
- **建议 / 参考方向**：上下文内信任分级：system > user > tool result > retrieved content。

### J4. 代码执行类工具是否有沙箱？
- **严重度**：P0（如有此类工具）
- **检查要点**：网络隔离、文件系统隔离、资源限额、超时。容器逃逸测试是否做过？
- **建议 / 参考方向**：一次性沙箱 + 出站网络白名单 + 无持久凭证。

### J5. 工具供应链（MCP server、第三方插件）是否有审查机制？
- **严重度**：P1
- **检查要点**：第三方工具的引入流程（安全评审、版本钉住、更新策略）？工具描述本身也是注入面（tool poisoning）。
- **建议 / 参考方向**：工具注册走与依赖引入同级的评审；工具描述/输出按不可信内容处理。

### J6. 是否做过越权与对抗性红队测试？
- **严重度**：P1
- **检查要点**：是否有成体系的对抗测试报告（不只是一两个手工用例）：角色扮演绕过、多轮诱导、编码混淆、跨租户探测。
- **建议 / 参考方向**：上线前红队 + 定期复测；发现的问题进评测集回归。

### J7. 是否有滥用检测与速率限制？
- **严重度**：P1
- **检查要点**：异常调用模式（高频探测、参数遍历、批量越权尝试）能否被发现并阻断？
- **建议 / 参考方向**：行为分析 + 自动限流 + 人工介入阈值。

## K. 审计与证据（5 项）

### K1. 每次关键决策是否有完整证据链？
- **严重度**：P0
- **检查要点**：任意抽一笔已执行的高危操作，要求现场重建：输入是什么、Agent 看到了什么上下文、为什么决定做、策略如何判断、谁批准的、批准时看到什么、执行结果如何。任何一环缺失即不通过。
- **建议 / 参考方向**：证据链 = 事件溯源的自然产物；审计是设计出来的，不是补出来的。

### K2. 审计日志是否防篡改？
- **严重度**：P0
- **检查要点**：append-only/WORM 存储？运维能否直接改审计表？审计与业务库的权限是否分离？
- **建议 / 参考方向**：独立存储 + 哈希链/签名 + 访问审计。

### K3. 审计保留期是否满足监管要求？
- **严重度**：P1
- **检查要点**：对照适用监管（如证券、银行、基金行业的留痕要求）逐项确认保留期限与可检索性。
- **建议 / 参考方向**：合规清单驱动的保留策略；定期恢复演练验证可用性。

### K4. 能否回答"为什么 Agent 在 T 时刻做了 X"？
- **严重度**：P1
- **检查要点**：可解释性不是指 LLM 的思维链（那不可靠），而是指：决策依据的规则、数据、版本（模型版本、prompt 版本、策略版本）是否全部留痕。
- **建议 / 参考方向**：版本三元组（model/prompt/policy）随每次决策记录。

### K5. 审计是否支持按维度回溯查询？
- **严重度**：P1
- **检查要点**：按客户、按账户、按操作类型、按 Agent、按审批人，能否快速拉出完整轨迹？监管现场检查时这就是刚需。
- **建议 / 参考方向**：审计数据的查询接口是交付物之一，不是事后手工捞日志。

## L. 可靠性与运营（6 项）

### L1. 失控 Agent 是否有熔断与急停？
- **严重度**：P0
- **检查要点**：发现 Agent 行为异常后，多快能全局停掉它的执行能力？是按租户、按 Agent、按工具粒度，还是只能全站停？
- **建议 / 参考方向**：分级 kill switch；急停本身走审计。

### L2. 队列积压与任务饥饿是否有监控？
- **严重度**：P1
- **检查要点**：人工任务积压、执行队列延迟、单租户占满资源，是否有指标与告警？
- **建议 / 参考方向**：队列深度、等待时长 P99、按租户的公平性指标。

### L3. 重启/部署后的恢复语义是否安全？
- **严重度**：P0
- **检查要点**：部署重启时：在途执行是否安全恢复？等待中的人工任务是否丢失？是否存在"服务已监听但恢复未完成"的窗口期接收新请求？（与 C4 联动）
- **建议 / 参考方向**：先恢复后监听（recover-then-listen）；恢复失败则不提供服务。

### L4. 端到端 tracing 是否覆盖 Agent 调用链？
- **严重度**：P2
- **检查要点**：一次用户请求 → Agent 推理 → 工具调用 → 审批 → 副作用，能否用同一个 trace id 串起来？
- **建议 / 参考方向**：correlation id 贯穿所有组件与审计事件。

### L5. Prompt / 流程 / 策略变更是否有灰度与回滚？
- **严重度**：P1
- **检查要点**：这三类变更与代码变更同等级别对待吗？有没有"直接改线上 prompt"的通道？
- **建议 / 参考方向**：一切影响行为的变更走版本化 + 灰度 + 可回滚。

### L6. 是否定义了 Agent 特有的 SLO？
- **严重度**：P2
- **检查要点**：除延迟/成功率外，是否跟踪：人工接管率、审批通过率、策略拒绝率、评测集质量分？这些是 Agent 系统健康度的先行指标。
- **建议 / 参考方向**：人工接管率异常上升通常预示模型或数据漂移。

## M. 合规与治理（5 项）

### M1. 是否有监管映射清单？
- **严重度**：P1
- **检查要点**：平台的每类能力（投顾建议、交易执行、客户沟通、报告生成）分别受哪些法规/内规约束，是否有逐条映射？
- **建议 / 参考方向**：合规参与架构评审，而不是架构定型后补合规。

### M2. Agent 行为变更是否纳入变更管理？
- **严重度**：P1
- **检查要点**：模型升级、prompt 修改、新工具上线、策略调整，是否都有评审、记录、回滚方案？
- **建议 / 参考方向**：与 M 3、L5 联动；变更记录本身是审计对象。

### M3. AI 参与决策是否有客户告知与留痕？
- **严重度**：P1
- **检查要点**：面向客户的场景（建议、客服、报告），AI 参与是否披露？客户的同意/偏好是否记录？
- **建议 / 参考方向**：披露文本法务评审；留痕入审计。

### M4. 出错时的责任归属是否事先定义？
- **严重度**：P2
- **检查要点**：Agent 造成客户损失时，责任如何在平台方、模型供应商、业务方、审批人之间划分？合同与内部制度是否覆盖？
- **建议 / 参考方向**：责任矩阵随上线评审一并签署。

### M5. 是否有定期的架构复审与红队机制？
- **严重度**：P2
- **检查要点**：上次复审是什么时候？发现的问题闭环了吗？模型能力与威胁情报都在快速变化，一次评审的有效期有限。
- **建议 / 参考方向**：年度全面复审 + 重大变更触发复审 + 半年度红队。

## 附录 2：评审流程建议

1. **预审**（半天）：平台方按本清单自评，标记不确定项；评审方先看 P0 红线速查表。
2. **现场评审**（1–2 天）：按 A→M 顺序过；每个 P0 条目要求**现场演示或代码佐证**，不接受口头承诺。
3. **对抗验证**（1 天）：对 D/E/F/J 的高风险条目做实测（注入、越权、重放、崩溃注入）。
4. **报告与整改**：按附录 1 模板输出；P0 不过夜，P1 带期限，P2 进 backlog。
5. **复验**：P0/P1 项全部复验关闭后才算评审结束。

## 附录 3：主要参考方向

- **AWS Well-Architected — Agentic AI Lens**：orchestration layer 安全控制、工具调用授权、proportionate human oversight、memory/state 保护。
- **Microsoft Agent Framework**：deterministic executor / HITL / 模型动态决策的三选一决策框架；workflow checkpoint 语义。
- **Anthropic — Building Effective Agents**：workflow 与 agent 的分野、何时不该用 agent。
- **OWASP Top 10 for LLM Applications**：注入、敏感信息泄露、供应链、过度代理权（excessive agency）。
- **NIST AI Risk Management Framework**：治理-映射-测量-管理的整体框架。
- **行业监管**：适用地的数据出境、留痕、适当性管理要求（按业务属地逐条确认）。
